## Verdict

No Medium-or-higher finding in the new code. What follows is what was
checked, the one apparent issue that dissolves on verification (E), and
four Info notes. This is a no-findings report with the edge cases, the
invariants, and the gaps left, as the bounty text allows.

## A. Dispatch (`jing-ladder-dispatch.clar`, 217 lines) — clean

- Validate-then-execute is atomic within one transaction: `validate-one`
  over all allocations runs before the first asset movement in
  `deposit-one`, and `validate-exit` runs before the first `exit-one`.
  No inter-transaction TOCTOU is possible.
- Budget accounting subtracts from `total` instead of summing caller uints
  (no addition overflow); exact-equality `remaining == u0` enforces
  sum-allocations == total; zero amounts, duplicates (`seen` list, max 10
  entries for max-10 lists — cannot overflow `as-max-len?`), and empty
  lists are all refused (u7101–u7105).
- Trait confusion is impossible: seating is checked against the LADDER's
  own maps (`is-band-x`/`is-band-y` for deposits, `get-registered` + side
  match for exits). A caller-supplied trait reference to an unregistered
  contract fails closed.
- `ERR_DIRECT_CALL` (tx-sender == contract-caller) keeps the helper from
  spending an intermediary's sender context; the rung pulls input assets
  from tx-sender directly, which is the user in both direct and dispatch
  flows. Proxy-class discussion is out of scope per the bounty text.
- Batch semantics are all-or-nothing by Clarity atomicity; a sold-out rung
  mid-batch aborts the whole batch (documented in-code; per-rung `claim`
  is the documented fallback). Matches `README-jing-ladder-dispatch.md`.

## B. Market-spread rungs vs fixed rungs — delta is peg-only, clean

Diffed `jing-buy-stx-market-spread.clar` against fixed `jing-buy-stx.clar`:
the only functional changes are `spread-bps`/`floor-cents`/`floor`
(data-vars + getters + state), two-argument `initialize` with
`bps < 10000` (u7010) matching the market's `valid-spread`, on-chain
name check `jing-buy-stx-spread-<bps>-floor-<whole>-<frac>` (frac
zero-padded: 5 -> "05", verified), ladder key packing
`cents * 10000 + bps` (injective because bps < 10000, so two rungs can
share a spread at different floors without collision), side `"buy-peg"`
against its own canonical hash, and `push-to-market` passing the floor
with `(some spread-bps)`. All accounting, `sync`, withdraw math,
`settle-proceeds`, and epoch logic are untouched from the fixed rung.

## C. Buy-spread vs sell-spread mirror — clean

Every non-comment diff line is the expected x/y swap: SBTC-transfer vs
`stx-transfer?`, `held-sats`/`stx-accounted` vs `held-ustx`/`sats-accounted`,
`deposit-token-x`/`withdraw-token-x`/`cancel-token-x-deposit` vs the `-y`

identical on both sides.

## D. Ladder v1 seats (`jing-ladder-v1.clar`) — clean, invariant holds

- Invariant `band-count[side] == number of seated (side, spread) keys`
  holds on every path: free-seat `register` counts +1, replacement
  overwrites without counting, `register-unseated` counts nothing,
  `seat-band` reuses `claim-seat` (taken -> no count change, free ->
  +1, guarded by `ERR_ALREADY_SEATED`), `retire-band` deletes the key
  and counts -1 (key-existence implies count >= 1, so no underflow).
- Prior v6-2 finding J-1 (no ceiling on `set-max-band-per-side`) is
  FIXED: `n < MAX_SEATS_PER_SIDE (50)` is now enforced alongside the
  floor (lines 340–347).
- Owner-gated paths (`set-canonical`, `seat-band`, `retire-band`,
  `set-max-band-per-side`, two-step `propose/accept-owner` with 144-block
  timelock) require no further trust assumptions beyond the owner role.
- Post-replacement windows are safe: the replaced rung keeps its
  `registered` row, funds, and resting order; members can always withdraw
  and claim (see Info I-3 for the transient seat-protection lag).

## E. The gate change (v6-3 market delta) — the suspicious part that holds

The new `gate-bid-fold`/`gate-offer-fold` drop the `(>= amount min-deposit)`
check that `live-bid-fold`/`live-offer-fold` have. At first glance the gate
now fires on dust that can never fill — an over-blocking/DoS smell. It is
correct, and deliberately so (commit `9730bc44`: "gate sees small orders"):

- Settlement distribution (`distribute-to-token-y-depositor` L3026,
  `distribute-to-token-x-depositor` L3121) is strictly pro-rata over ALL
  depositors with NO minimum check: `my-token-x-received =
  my-deposit * settle-token-x-after-fee / total`. Sub-minimum orders DO
  fill in the batch. The gate (which guards batch admission) must therefore
  see them too. Verified, not assumed.
- The gate formulas match the reviewed spec in
  `README-audit-v6-2-rebate-gate.md`: book scan at `min(limit, mid+0.4%)`
  for bids / `max(limit, mid-0.4%)` for asks. All eight gate sites use the
  new functions (L1285, L1428, L1662, L1697 asserts; L1735, L1770, L1842,
  L1918 boolean contexts); `would-take-as-x/y` remain for the
  reprice-or-swap "crosses right now" question (L1816, L1890), as documented.
- Remaining hardening in the delta: six depositor-list adds use
  `unwrap! ERR_QUEUE_FULL` instead of `unwrap-panic`; seat reads point at
  `.jing-ladder-v1`; `sync-seat-count` prunes stale seats before refresh.

## F. Arithmetic bounds (checked, no overflow)

- Peg math: `mid * (10000 +/- s)` with mid ~1e16-class values stays orders
  of magnitude below uint128; `1e18 / cents` requires `cents > u0`
  (enforced before division); degenerate huge `cents` truncates the floor
  to 0, which only unbinds the guard for that deploy.
- Withdraw ceil-division `((amount * SCALE) + fi - 1) / fi`: `fi > 0` is
  guaranteed post-`sync` (epoch-close resets to SCALE, otherwise
  `fi >= SOLD_OUT_INDEX`), and the shares==0 sync branch cannot reach the
  division (old-epoch positions settle-and-delete first, ending in a clean
  `ERR_NO_POSITION`).
- `stx/sats-accounted` watermark: the shares==0 reset (`= current balance`)
  preserves the pay-out invariant by induction — total owed across surviving
  old-epoch positions never exceeds the balance present at reset, and no
  other path moves the asset out.

## Info notes (no severity claimed)

- I-1: `register`, band path, wraps `claim-seat` in a vacuous
  `(is-some ...)`: on a free seat the value is `false` but it is discarded
  and registration proceeds correctly (count was already incremented inside
  `claim-seat`). Dead logic, zero behavioral effect.
- I-2: `sync-seat-count` and `prune-seats` have identical bodies.
- I-3: after a band replacement, the market's `seated-x/y` lists still
  protect the OLD rung until anyone calls the permissionless
  prune/sync-seat; the NEW rung rests unprotected meanwhile (worst case it
  is bumped to parked — funds safe, availability wrinkle only).
- I-4: assets sent directly to a rung contract (not via `deposit`) are
  absorbed into the held watermark at the next `sync` and become
  unclaimable dust. Self-inflicted only.
